FEATURE 3Corners: from 8 pixel rounds to sharp

Today every shadcn and Base UI component shares --radius: 8px, the scrollbar thumb is a full pill (border-radius: 9999px), and several hand styled cards use 8px too. The proposal removes rounding everywhere and lets hairlines and spacing carry the structure instead. One exception: the switch knob stays a circle, because it is a knob and reads as hardware, not as a rounded corner.

Outer window frame corners Controlled by the OS window manager (KDE, for example, rounds its own frame on some themes). The app cannot change that from inside; all inner surfaces are what this plan controls.

Small print: with rounds gone, one extra hairline of definition helps. Buttons and rows get a 1px border (or inset shadow) in the new hairline color, which the component gallery below shows. If 0px ever feels too raw on the eye, the fallback is 2px; the checklist asks for the final call.

FEATURE 3Palette: graphite instrument, signal cyan

The current palette is a warm graphite with amber accents (--color-accent: #d8a44c dark, #d97706 light). The proposal keeps the instrument panel feel but moves the accent to a cool signal cyan, which reads better on translucent dark glass, and it builds every surface color as a pair: a solid fallback plus an alpha version for the glass modes. Amber stays available as an alternate accent; the checklist asks which one to keep.

FEATURE 3Translucency: three levels

Translucency is planned as a user setting with three levels, so slow machines and picky compositors do not pay for blur they cannot afford. Press the buttons to compare. All three mockups deliberately use the same wallpaper behind the window to make the difference visible.

FEATURE 4Speed test: where it lives

The test is for the moment before a download starts: a link is pasted, and the user wants to know what the networks can do before committing to a big file. So the primary entry point is a Test speed button inside New Download, next to the networks row. A second entry point in the Networks menu ("Test networks...") is proposed so the test can also run without a link; the checklist asks if that is wanted in version one.

Test target rule: if the pasted link answers a small range request (the probe the app already runs), the test downloads from that same URL when it is a file. Otherwise it uses the default test endpoint, which is configurable, and the dialog always shows the target before the test starts. No result or measurement ever leaves the machine; the only network use is the download the user asked for.

FEATURE 4Measurement plan, the rules behind the numbers

These rules exist so the comparison is fair and the numbers mean something. They are requirements for the implementation, shown here without code.

Stage Networks in use Streams Warm-up Measure window What it produces
Probe (per selected network) That network only 1 none one 64 KB range request Reachable, or Unreachable with a reason
Alone stage (per reachable network) That network only 8 on it 2 s, counted for data use but not for rate 10 s, or 100 MB cap That network's Mbps
Combined stage All reachable networks together 8 split as evenly as possible (remainder goes to the fastest alone stage) same 2 s same 10 s / 100 MB Combined Mbps, per network bytes for contribution
  • Same stream count everywhere. All stages use 8 streams, the app's standard setting, so a single stream test does not undersell a link and the combined stage compares like with like. (One TCP stream can mask capacity it is not allowed to use; eight can hide it too, but at least the comparison is fair between stages.)
  • Warm-up first, then measure. The first 2 s of every stage are discarded from the rate because TCP starts slow (congestion window ramp) and speed of a link is about its steady state.
  • Mbps math. Rate = measured bytes x 8 / 1,000,000 / seconds. The dialog shows Mbps as the headline, MB/s in mono as secondary, matching the app's speed unit setting.
  • Bodies are discarded. Every ranged GET is read in chunks and dropped; nothing touches the disk, staging files are never involved, and no test file is created anywhere. A cancel aborts all streams in one step through one controller.
  • Reachability first. Each selected network is probed before any measuring. An unreachable network is reported explicitly, kept out of the combined stage, and still shown in the results table.
  • Sequential, so state changes matter. Stages run one at a time (parallel per network tests would compete for the shared upstream and for disk and CPU, and would not answer "what can each one do"). The dialog says so, in the results notes.

FEATURE 4Implementation sketch (for the build step)

  • Main process module: a new speedtest.ts next to the download engine that reuses the existing per interface socket binding, the per network meters, and the range request code, without the block planner and without writing files. It owns the stage machine: probe, then stages in order, then combined.
  • IPC: speedtest:start (selected network ids and the target URL), speedtest:update events for live progress, speedtest:cancel, and a final result payload (per network Mbps, combined, contributions, unreachable list, bytes used). Typed through the same contract file the other channels use.
  • Renderer: a SpeedTestDialog component in the new style, opened from New Download and optionally from the Networks menu. It only renders state from the update events; no measurement logic in the renderer.
  • Persistence: none in version one. Results live for the session; a "last result" chip could appear next to the networks row (roadmap, not this plan).
  • Feature 3 order of work: palette and radius tokens first (one file, entire app follows), then component pass for the few hand styled surfaces, then the material setting with its fallbacks. The speed test is then built directly in the new style, so it never needs a redesign later.
