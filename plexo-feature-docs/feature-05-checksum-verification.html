Feature 05 · Wifi-Merger

Checksum Verification & Intelligent Chunk Repair

After a file is assembled from chunks pulled over multiple network interfaces, Wifi-Merger verifies the final result against a known checksum — and if it fails, re-downloads only the corrupted chunks instead of the entire file.

02The problem

Wifi-Merger's core advantage is also its biggest new risk. A single file is split into chunks of 1–8 MB and streamed in parallel across Wi‑Fi, Ethernet, USB tethering, and hotspots. Any one of those links can drop, stall, or deliver a truncated response body while still returning a 200 OK. The download "succeeds" and the file is assembled — but the result may not be bit-identical to the source.

Before this feature, the app only validated that the remote file had not changed between pauses (via ETag / Last-Modified). There was no end-to-end check on the local assembled file, and no way to fix a bad chunk short of deleting and restarting the download.

Failure mode: a corrupted 4 MB chunk in a 6 GB ISO means the whole file must be discarded. For OS images, datasets, and installers, that is hours of wasted bandwidth — much of it on metered mobile connections.

03How it works

The feature is a three-stage pipeline that runs automatically at the end of every direct download, plus an on-demand "Manual Verify" action for completed files.

Stage 1 — Acquire the expected hash

The expected checksum is resolved from the first available source:

  1. User input — the optional "Checksum" field in the New Download dialog.
  2. HTTP header — Content-MD5 (base64) or a Digest header when present.
  3. Sidecar file — e.g. ubuntu.iso.sha256 or SHA256SUMS sitting next to the target.
  4. None found — verification is skipped and the download behaves exactly as it did before this feature.

Stage 2 — Verify the assembled file

After the final chunk is committed to disk, the download manager calls verifyDownload(id, expectedHash). The verifier streams the file through Node's crypto.createHash() (constant memory, no full file in RAM) and compares the digest. On a match the task is marked Verified and the pipeline ends.

Stage 3 — Intelligent repair

On mismatch, the repair engine takes over. It picks one of two strategies depending on what metadata the source exposes:

Strategy A · preferred

Per-chunk hashes available

  1. Re-hash each cached chunk locally — no network I/O.
  2. Mark only the chunks whose digest differs.
  3. Re-fetch those chunks over the best available interface.
  4. Re-verify the full file.
Strategy B · fallback

Whole-file hash only

  1. Hash the first and second half of the file.
  2. Recurse into whichever half (or both) mismatches.
  3. Stop at chunk granularity — a binary search over the file.
  4. Re-fetch only the chunks inside the corrupted region.

Why not just re-download? Re-fetching the whole file defeats the purpose of a download manager. On a 6 GB image with one bad 4 MB chunk, targeted repair moves roughly 1,500× less data than a full restart.

Module API

// plexo/src/main/download/checksum.ts

export type HashAlgorithm = 'md5' | 'sha1' | 'sha256';

export type VerificationStatus =
  | 'skipped'   // no expected hash could be resolved
  | 'verifying'
  | 'verified'
  | 'repairing'
  | 'failed';

export interface VerificationResult {
  match: boolean;
  algorithm: HashAlgorithm;
  expectedHash: string;
  actualHash: string;
  corruptedRanges?: ByteRange[];  // populated on mismatch
}

/** Streamed hash — constant memory, safe for multi-GB files. */
export function computeFileHash(
  filePath: string,
  algorithm: HashAlgorithm
): Promise<string>;

/** Resolve an expected hash from input, headers, or a sidecar file. */
export function resolveExpectedHash(
  downloadId: string,
  explicit?: string
): Promise<{ hash: string; algorithm: HashAlgorithm } | null>;

/** Entry point, called by the download manager on completion. */
export function verifyDownload(
  downloadId: string,
  expectedHash: string
): Promise<VerificationResult>;

/** Strategy A or B, then re-fetch via the bandit-ranked interface. */
export function repairCorruptedChunks(
  downloadId: string,
  corruptedRanges: ByteRange[]
): Promise<void>;

{

  "repairAttempts": 1,
  "chunkHashes": ["a41d…", "7c90…", "…"]   // optional, Strategy A only
}

No new dependencies. Everything is built on Node's crypto module and the existing chunk map. The verifier streams the file rather than buffering it, so memory use stays flat regardless of file size.

07Interface selection for repair

A repair is a small, high-value transfer, so it should not simply reuse whatever link happens to be active. The repair engine queries the existing contextual bandit in learning/bandit.ts for a ranked list of interfaces, then:

  • Picks the highest-ranked interface that is currently up.
  • Falls back to the next-ranked interface if the chosen one fails or stalls.
  • Respects per-adapter data quotas configured in the CLI, so a repair never quietly blows through a metered hotspot's cap.

Because the bandit already tracks throughput, latency jitter, and time-of-day patterns, repairs automatically favour the link that has historically been most reliable — without any new learning logic.

08CLI usage

Where the project exposes a CLI entry point, verification is opt-in via a flag:

# Verify against a SHA-256 digest
plexo download https://example.org/ubuntu-24.04.iso \
  --checksum sha256:9b2c1f4e…

# MD5, bare hex (algorithm inferred by length)
plexo download https://example.org/tool.zip --checksum 5d41402abc4b2a76b9719d911017c592

# Auto-detect from a sidecar file next to the target
plexo download https://example.org/data.tar.gz --checksum auto

09Edge cases

SituationExpected behaviour
No checksum supplied and none detectable Verification is skipped. Download proceeds exactly as before the feature existed.
Unrecognised algorithm string Fall back to SHA-256 and log a warning; never hard-fail the download over a parse error.
Target file already exists Verify the existing file first. If it matches, skip the download entirely.
App closed mid-repair Repair state is persisted with the chunk map; the repair resumes on next launch.
Selected interface dies mid-repair Automatically re-queue the remaining chunks on the next-ranked interface from the bandit.
Repair fails 3 times Status becomes failed; corrupted chunk indices are written to the log for manual diagnosis.
Source changed since chunks were fetched Re-verify ETag/Last-Modified before re-fetching; if changed, abort repair rather than mix versions.
Torrent downloads Out of scope. Torrent piece verification already handles integrity.
